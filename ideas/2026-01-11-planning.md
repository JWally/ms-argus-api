**Date:** 2026-01-11
**Status:** Post-V4 Improvements

## Executive Summary

The codebase is **architecturally sound** with clean tiered matching, good separation of concerns, and proper dependency injection. However, several issues need addressing before 30B requests/year scale:

| Priority | Issue                                   | Risk                 |
| -------- | --------------------------------------- | -------------------- |
| P0       | Math.random() UUID generation           | Device ID collisions |
| P0       | No env var validation                   | Runtime crashes      |
| P1       | CORS wildcard with credentials          | Security violation   |
| P1       | console.log bypasses structured logging | Observability gap    |
| P2       | Undocumented critical decisions         | Maintainability      |
| P2       | Orphaned connections from Promise.race  | Resource exhaustion  |

## Phase 1: Critical Fixes (Do First)

### 1.1 Replace Math.random() with crypto.randomUUID()

**File:** `src/services/matching/matching-service.ts:509-515`

**Current (Bad):**

```typescript
export function generateUUID(): string {
  return "xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx".replace(/[xy]/g, (c) => {
    const r = (Math.random() * 16) | 0;
    const v = c === "x" ? r : (r & 0x3) | 0x8;
    return v.toString(16);
  });
}
```

**Should Be:**

```typescript
import { randomUUID } from "crypto";

export function generateUUID(): string {
  return randomUUID();
}
```

**Why:** Math.random() is not cryptographically secure. At 30B requests/year, collision probability becomes non-trivial. Device ID uniqueness is critical for fraud detection.

**Test:** Add collision test with 1M generated UUIDs.

### 1.2 Validate Environment Variables at Startup

**File:** `src/handlers/matching-worker.ts`, `src/handlers/profile-updater.ts`

**Current (Bad):**

```typescript
const tier1IndexTable = process.env.TIER1_INDEX_TABLE!;
const tier2BucketsTable = process.env.TIER2_BUCKETS_TABLE!;
```

**Should Be:**

```typescript
// src/config/env.ts (new file)
export interface EnvConfig {
  PROFILES_TABLE: string;
  TIER1_INDEX_TABLE: string;
  TIER2_BUCKETS_TABLE: string;
  REDIS_HOST: string;
  // ...
}

export function getValidatedEnv(): EnvConfig {
  const required = [
    "PROFILES_TABLE",
    "TIER1_INDEX_TABLE",
    "TIER2_BUCKETS_TABLE",
    "REDIS_HOST",
  ];

  const missing = required.filter((k) => !process.env[k]);
  if (missing.length > 0) {
    throw new Error(`Missing required env vars: ${missing.join(", ")}`);
  }

  return {
    PROFILES_TABLE: process.env.PROFILES_TABLE!,
    // ... validated values
  };
}
```

**Why:** Non-null assertions (`!`) crash at runtime when env var is missing. Fail fast at startup with clear error message.

### 1.3 Fix CORS Configuration

**File:** `src/helpers/constants.ts:35`

**Current (Bad):**

```typescript
const HARDENED_ORIGIN = "*";

export const MIDDY_CORS_CONFIG: Options = {
  origin: HARDENED_ORIGIN, // ALLOWS ALL ORIGINS
  credentials: true, // + credentials = invalid per CORS spec
};
```

**Should Be:**

```typescript
const ALLOWED_ORIGINS = [
  "https://app.argus.example.com",
  "https://dashboard.argus.example.com",
];

export const MIDDY_CORS_CONFIG: Options = {
  origins: ALLOWED_ORIGINS,
  credentials: true,
};
```

**Why:** `origin: "*"` with `credentials: true` is explicitly forbidden by CORS specification. Browsers will reject this configuration.

## Phase 2: Observability & Consistency

### 2.1 Replace console.log with Structured Logger

**Files:**

- `src/services/get-aws-secrets.ts`
- `src/services/rotate-aws-secrets.ts`
- `src/helpers/middy-helpers.ts`

**Current (Bad):**

```typescript
console.error("Error retrieving secret:", error);
console.log("Secret rotated successfully", {...});
```

**Should Be:**

```typescript
import { Logger } from "@aws-lambda-powertools/logger";
const logger = new Logger({ serviceName: "argus-secrets" });

logger.error("Error retrieving secret", { error });
logger.info("Secret rotated successfully", {...});
```

**Why:** Console.log bypasses structured logging. No correlation IDs, no log levels, harder to query in CloudWatch.

## Phase 3: Robustness Improvements

### 3.1 Fix Promise.race Orphaned Connections

**File:** `src/services/matching/matching-service.ts:208-236`

**Current (Bad):**

```typescript
const TIMEOUT_SENTINEL = Symbol("timeout");
const raceResult = await Promise.race([
  tier2CompoundMatch(fingerprint), // This gets abandoned!
  timeoutPromise,
]);
```

**Should Be:**

```typescript
const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort(), TIER2_TIMEOUT_MS);

try {
  const result = await tier2CompoundMatch(fingerprint, controller.signal);
  clearTimeout(timeoutId);
  return { result, timedOut: false };
} catch (error) {
  if (error.name === "AbortError") {
    return { result: null, timedOut: true };
  }
  throw error;
}
```

**Why:** Promise.race doesn't cancel the losing promise. DynamoDB connections from tier2CompoundMatch continue running in background, potentially exhausting Lambda connection pool.

### 3.2 Add Startup Health Checks

**Files:** Both handlers

```typescript
// Add before handler registration
let initialized = false;

async function initializeOnce(): Promise<void> {
  if (initialized) return;

  // Validate config
  const config = getValidatedEnv();

  // Test critical connections (with short timeout)
  await Promise.all([
    redis.ping(),
    dynamodb.send(
      new DescribeTableCommand({ TableName: config.PROFILES_TABLE }),
    ),
  ]);

  initialized = true;
}
```

**Why:** Fail fast on misconfiguration. Don't wait for first request to discover broken connections.

## Phase 5: Bloom Filter Implementation

### Design (From Architecture Doc)

| Filter                    | Purpose                      | Size    |
| ------------------------- | ---------------------------- | ------- |
| `bf:{tenant}:stable_hash` | Skip Tier1 stable hash reads | ~12.5MB |

### Implementation Plan

1. **Week 1: Redis Bloom Filter Module**

   ```typescript
   // src/services/bloom/bloom-filter.ts
   export class BloomFilter {
     constructor(
       private redis: Redis,
       private name: string,
       private expectedItems: number = 10_000_000,
       private falsePositiveRate: number = 0.01,
     ) {}

     async add(item: string): Promise<void>;
     async mightContain(item: string): Promise<boolean>;
     async clear(): Promise<void>;
   }
   ```

2. **Week 2: Integration with Matching Service**
   - Check bloom filter before Tier1 DynamoDB read
   - Update bloom filter in ProfileUpdater on write
   - Add metrics: `BloomFilterHit`, `BloomFilterMiss`, `BloomFilterFalsePositive`

3. **Week 3: Weekly Rebuild Job**
   - Lambda on EventBridge schedule (weekly)
   - Scans Profiles table, rebuilds bloom filter
   - Handles TTL'd devices that left stale entries

### Expected Savings

- 50% of requests are "new devices" with no match
- Skip 2-3 DynamoDB reads per new device
- ~$11K/year DynamoDB read cost savings
