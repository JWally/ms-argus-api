# Async Processing Latency Analysis & Gameplan

**Date:** 2026-01-12
**Issue:** 20+ second delays in async processing vs 3-second SLA requirement

## Executive Summary

Integration tests require 60-second timeout windows to pass, masking a fundamental architecture problem: SQS batch windowing introduces 15-20 seconds of latency before any processing begins. With a 3-second SLA ceiling, the current configuration is unacceptable for production.

## Root Cause Analysis

### Primary Culprit: Profile Queue Batching (50% of latency)

**Location:** `lib/constructs/workers.ts:201-207`

```typescript
profileUpdater.addEventSource(
  new SqsEventSource(queues.profileQueue, {
    batchSize: 10,
    maxBatchingWindow: Duration.seconds(10), // <-- PRIMARY ISSUE
    reportBatchItemFailures: true,
  }),
);
```

The `maxBatchingWindow: 10 seconds` means Lambda will wait up to 10 seconds to accumulate messages before triggering, even if messages arrive immediately.

### Secondary Culprit: Matching Queue Batching (25% of latency)

**Location:** `lib/constructs/workers.ts:157-163`

```typescript
matchingWorker.addEventSource(
  new SqsEventSource(queues.matchingQueue, {
    batchSize: 10,
    maxBatchingWindow: Duration.seconds(5), // <-- SECONDARY ISSUE
    reportBatchItemFailures: true,
  }),
);
```

Combined with profile queue, worst case = 15 seconds of batching delay alone.

### Additional Latency Sources

1. **Lambda Cold Starts (1-2 seconds)**
   - VPC-attached Lambdas have longer cold starts
   - No provisioned concurrency configured

2. **SQS Visibility Timeout (60 seconds)**
   - Location: `lib/constructs/queues.ts`
   - Not a latency source, but indicates expectation of slow processing

3. **Test Masking**
   - `tests/integration/matching-flow.spec.ts` uses 20 attempts × 3 seconds = 60 seconds tolerance
   - Tests pass but hide the real latency problem

## Latency Breakdown (Current State)

| Component                      | Worst Case | Typical  |
| ------------------------------ | ---------- | -------- |
| ECS → SQS (Matching)           | ~100ms     | ~50ms    |
| SQS Batching Window (Matching) | 5s         | 2-3s     |
| Lambda Cold Start (Matching)   | 2s         | 0-500ms  |
| Matching Processing            | ~500ms     | ~200ms   |
| SQS → Profile Queue            | ~100ms     | ~50ms    |
| SQS Batching Window (Profile)  | 10s        | 5-7s     |
| Lambda Cold Start (Profile)    | 2s         | 0-500ms  |
| Profile Processing             | ~500ms     | ~200ms   |
| DynamoDB Write                 | ~100ms     | ~50ms    |
| **Total**                      | **~20s**   | **~10s** |

## Recommended Changes

### Phase 1: Eliminate Batching Windows (Immediate - addresses 75% of latency)

Reduce batching windows to near-zero while keeping batch size for efficiency:

```typescript
// Profile Queue - reduce from 10s to 100ms
profileUpdater.addEventSource(
  new SqsEventSource(queues.profileQueue, {
    batchSize: 10,
    maxBatchingWindow: Duration.millis(100), // Was: 10 seconds
    reportBatchItemFailures: true,
  }),
);

// Matching Queue - reduce from 5s to 500ms
matchingWorker.addEventSource(
  new SqsEventSource(queues.matchingQueue, {
    batchSize: 10,
    maxBatchingWindow: Duration.millis(500), // Was: 5 seconds
    reportBatchItemFailures: true,
  }),
);
```

**Trade-off:** More Lambda invocations = higher cost. At current volume, negligible. At scale, may need to revisit.

### Phase 2: Add Provisioned Concurrency (Addresses cold starts)

```typescript
// In workers.ts - add provisioned concurrency
const matchingWorkerAlias = new lambda.Alias(this, "MatchingWorkerAlias", {
  aliasName: "live",
  version: matchingWorker.currentVersion,
  provisionedConcurrentExecutions: 2, // Keep 2 warm
});

const profileUpdaterAlias = new lambda.Alias(this, "ProfileUpdaterAlias", {
  aliasName: "live",
  version: profileUpdater.currentVersion,
  provisionedConcurrentExecutions: 2,
});
```

**Cost:** ~$15-20/month per Lambda with provisioned concurrency
**Benefit:** Eliminates 1-2 second cold starts

### Phase 3: Update Integration Test Expectations

Once latency is fixed, tighten test tolerances:

```typescript
// In matching-flow.spec.ts
const MAX_WAIT_MS = 5000; // Was effectively 60 seconds
const POLL_INTERVAL_MS = 500; // Was 3 seconds
```

## Alternative Architectures Considered

### Option A: Lambda Function URLs (Not Recommended)

- Could bypass SQS entirely for synchronous processing
- Loses decoupling, retry semantics, and backpressure handling
- Not appropriate for this use case

### Option B: Step Functions (Overkill)

- Would provide orchestration but adds complexity
- Better for complex workflows, not simple queue processing
- Would increase latency, not reduce it

### Option C: EventBridge Pipes (Viable Alternative)

- Could replace SQS → Lambda integration
- More efficient batching controls
- Worth evaluating if Phase 1 is insufficient

### Option D: Direct DynamoDB Streams (Not Applicable)

- Good for DynamoDB-triggered workflows
- Doesn't apply here since trigger is from ECS ingestion

## Decision Required

**Recommended:** Implement Phase 1 immediately (batching window reduction). This is low-risk, easily reversible, and addresses 75% of the latency problem.

**Phase 2** (provisioned concurrency) can be deferred until we confirm Phase 1 results and determine if sub-2-second latency is required.

## Files to Modify

1. `lib/constructs/workers.ts` - Reduce maxBatchingWindow values
2. `tests/integration/matching-flow.spec.ts` - Tighten timing expectations (after deployment)

## Risk Assessment

| Risk                       | Likelihood | Impact | Mitigation                        |
| -------------------------- | ---------- | ------ | --------------------------------- |
| Increased Lambda cost      | Medium     | Low    | Monitor CloudWatch billing        |
| Lambda throttling at scale | Low        | Medium | Configure reserved concurrency    |
| Breaking existing behavior | Very Low   | Low    | Batching still works, just faster |

## Conclusion

The 20-second latency is not a fundamental architecture problem - it's a configuration issue. The SQS batching windows were likely set conservatively during initial development and never tuned. Reducing them to sub-second values will bring latency well under the 3-second SLA with minimal risk.

# Part 2: Environment-Specific Configuration Strategy

## The Problem

The codebase has **60+ hardcoded configuration values** that should vary between dev and prod. Currently:

- Dev runs expensive production-like infrastructure
- Prod uses conservative dev-friendly timeouts
- No centralized configuration management
- Each construct has its own hardcoded values

**Only 5 values (8%) are currently environment-aware.** The rest are hardcoded.

## Enterprise Pattern: Centralized Config by Stage

Create a single source of truth for environment-specific configuration:

```typescript
// lib/config/stage-config.ts
import { Duration } from "aws-cdk-lib";

export interface StageConfig {
  // Lambda
  lambda: {
    matching: { memory: number; timeout: Duration; concurrency: number };
    profile: { memory: number; timeout: Duration; concurrency: number };
    provisionedConcurrency: number;
  };
  // SQS
  sqs: {
    visibilityTimeout: Duration;
    retentionPeriod: Duration;
    maxReceiveCount: number;
    batchingWindow: { matching: Duration; profile: Duration };
  };
  // ECS
  ecs: {
    cpu: number;
    memory: number;
    desiredCount: number;
    minCapacity: number;
    maxCapacity: number;
  };
  // Redis
  redis: {
    snapshotRetention: number;
  };
  // Alarms
  alarms: {
    lambdaErrorThreshold: number;
    lambdaThrottleThreshold: number;
    queueBacklogThreshold: number;
    cpuThreshold: number;
  };
  // Application
  app: {
    cacheTtlSeconds: number;
    profileTtlDays: number;
    tier2BucketTtlDays: number;
    dedupeCacheMaxEntries: number;
  };
}

    sqs: {

      retentionPeriod: Duration.days(1),

        matching: Duration.millis(500),

  },
  prod: {

export function getStageConfig(stage: string): StageConfig {
  // Default to dev for any non-prod stage
  return STAGE_CONFIGS[stage] || STAGE_CONFIGS.dev;
}
```

## Usage in Constructs

```typescript
// lib/constructs/workers.ts
import { getStageConfig } from "../config/stage-config";

export class Workers extends Construct {
  constructor(scope: Construct, id: string, props: WorkersProps) {
    const config = getStageConfig(props.stage);

    const matchingWorker = new NodejsFunction(this, "MatchingWorker", {
      memorySize: config.lambda.matching.memory,
      timeout: config.lambda.matching.timeout,
      reservedConcurrentExecutions: config.lambda.matching.concurrency,
      // ...
    });

    matchingWorker.addEventSource(
      new SqsEventSource(queues.matchingQueue, {
        batchSize: 10,
        maxBatchingWindow: config.sqs.batchingWindow.matching,
        reportBatchItemFailures: true,
      }),
    );
  }
}
```

## Summary

This is the enterprise-standard approach:

1. **Single source of truth** - One file defines all environment differences
2. **Type-safe** - TypeScript interface ensures completeness
3. **Easy to audit** - All env-specific values in one place
4. **Easy to extend** - Add new stages (staging, qa) trivially
5. **No magic** - Clear, explicit configuration

The immediate win is fixing the latency issue. The broader refactor to centralized config can be done incrementally alongside regular feature work.
