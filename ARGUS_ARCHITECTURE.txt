# ARGUS API Architecture
# Last Updated: 2026-01-11
# Status: V4 - Production Ready

================================================================================
## OVERVIEW
================================================================================

High-throughput device fingerprint ingestion and matching pipeline for fraud
detection. Designed for 30B requests/year (~950 QPS avg, ~3K QPS peak).

Cost Target: ~$3.50/million requests (~$105K/year at full scale)

## TIERED MATCHING STRATEGY
================================================================================

| Tier | Method          | Confidence | Latency | Expected Hit Rate |
|------|-----------------|------------|---------|-------------------|
| T0   | Redis Cache     | N/A        | <1ms    | 70% (repeat sess) |
| T0.5 | Evercookie      | 0.99       | 5-10ms  | 5%                |
| T1   | Stable Hash     | 0.95       | 5-10ms  | 10%               |
| T1   | Fuzzy Hash      | 0.85       | 5-10ms  | 5%                |
| T2   | Compound Filter | 0.6-0.85   | 20-50ms | 5%                |
| New  | Create Device   | 1.0        | N/A     | 5%                |

Tier 2 has a configurable timeout (default 50ms). If it times out, we "fail
open" and create a new device. The `Tier2Timeout` CloudWatch metric tracks this.

Future: Tier 3 vector similarity search (Qdrant) for hard cases.

## DATA LAYER SCHEMA
================================================================================

### Profiles Table
- PK: `tenant_id` (String)
- SK: `device_id` (String)
- Attributes: All fingerprint signals, risk_score, flags, timestamps
- TTL: 60 days

### Tier1Index Table
- PK: `tenant_id` (String)
- SK: `hash_key` (String) - e.g., "stable#abc123", "evercookie#uuid"
- Attributes: device_id, ttl
- TTL: 60 days

### Tier2Buckets Table (V2 - Adjacency List Pattern)
- PK: `bucket_key` (String) - e.g., "tenant#ip_ja4#192.168.1.1#ja4hash"
- SK: `device_id` (String)
- Attributes: ttl
- TTL: 60 days

IMPORTANT: Uses adjacency list pattern (one item per device) instead of
String Sets. This avoids the 400KB DynamoDB item limit that would be hit
with high-cardinality buckets (e.g., corporate NAT + common browser).

Query pattern: `KeyConditionExpression: bucket_key = :bk` returns all
device_ids in that bucket.

### Redis Keys
- `session:{session_id}` - Match result cache (15 min TTL)
- `recently_updated:{device_id}` - Mutation gate (1 hour TTL)
- `bf:{tenant_id}:{filter_type}` - Bloom filters (TODO: Phase 1)

## BLOOM FILTER DESIGN (PHASE 1 - TODO)
================================================================================

Purpose: Skip DynamoDB reads for devices that definitely don't exist.

### Filters to Implement
| Key Pattern                    | Purpose                      |
|--------------------------------|------------------------------|
| `bf:{tenant}:stable_hash`      | Skip Tier1 stable hash reads |

### Implementation
- Storage: Redis SETBIT/GETBIT (manual bloom filter)
- Size: ~12.5 MB per filter (10M devices, 1% FPR)
- Update: On profile creation/update in ProfileUpdater Lambda
- Check: Before DynamoDB read in MatchingWorker Lambda
- Rebuild: Weekly job to handle TTL'd devices (TODO: Phase 2)

### Expected Savings
- 50% of requests are "new devices" with no match
- Skip 2-3 DynamoDB reads per new device = 20-30ms latency reduction
- ~$11K/year DynamoDB read cost savings

- DynamoDB throttling (any table)
- Lambda error rate > 1%
- SQS DLQ message count > 0
- Redis connection failures

### Logging
- Structured JSON via Lambda Powertools
- Correlation: session_id, tenant_id, device_id
- Log levels: INFO for flow, WARN for degraded, ERROR for failures

## GO INGESTION SERVICE
================================================================================

Location: `cmd/ingestion/`

Ultra-thin HTTP handler optimized for throughput:

```go
type FingerprintPayload struct {
    SessionID   string            `json:"session_id"`
    TenantID    string            `json:"tenant_id"`
    Fingerprint json.RawMessage   `json:"fingerprint,omitempty"`  // Delayed parsing
    TCPBlob     string            `json:"tcp_blob,omitempty"`
    TLSBlob     string            `json:"tls_blob,omitempty"`
    Headers     map[string]string `json:"headers,omitempty"`
    Timestamp   int64             `json:"timestamp"`
}
```

Key design decisions:
- `json.RawMessage` for fingerprint: Avoids decode/re-encode overhead
- Immediate 204 response: No blocking on SQS
- Graceful shutdown: Drains in-flight requests on SIGTERM
- Structured logging: slog with JSON output

## SECURITY
================================================================================

### Edge Protection
- CloudFront + WAF with rate limiting
- WAF rules: SQL injection, XSS, known bad bots

### Secrets Management
- AWS Secrets Manager for API keys
- Automatic rotation every 30 days (rotate-aws-secrets Lambda)
- 15-minute cache in workers (KEY_CACHE_DURATION)

### Data Protection
- All data encrypted at rest (DynamoDB, S3, Redis)
- TLS 1.2+ for all connections
- No PII stored (fingerprints are device identifiers, not user data)

### Known Risks
- "Fail open" on Tier2 timeout: Tracked via Tier2Timeout metric
- No per-tenant rate limiting: Global WAF only (TODO: consider)
